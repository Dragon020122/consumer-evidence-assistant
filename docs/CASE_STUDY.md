# 项目复盘：从材料堆到可核对的事实链

## 背景与目标用户

预付式消费退费场景中的订单、服务协议、聊天记录和商家信息往往分散，用户难以说明“发生了什么、依据是什么、还缺什么”。目标用户是需要整理自己材料的普通消费者，以及需要查看已分配案件的人工复核人员。

本项目不是法律服务：它的目标是把材料整理成可回溯、可确认的结构，而不是给出责任、违法或结果判断。

## 为什么选择这个切口

预付式消费服务的材料类型相对明确，又同时具备时间顺序、金额、主体、沟通记录与剩余服务等典型信息，适合验证“非结构化材料 → 人工确认 → 可追溯整理”的 MVP 闭环。

## MVP 范围

范围包括案件创建、私有上传、Mock 提取、字段确认、时间线、事实—证据矩阵、缺口提示、草稿、导出、三角色复核和删除。明确不做支付、政府投诉提交、律师撮合、结果预测、自动赔偿计算和更多纠纷类型。

## 核心工作流与 AI 参与方式

用户上传材料后，适配层产生结构化候选值，并附带来源定位与置信度。Zod 校验失败会重试或进入人工处理；用户确认前，候选值不进入后续事实整理。时间线事件必须有证据回链，或被标记为用户陈述；矩阵和缺口规则只说明材料支持程度，不做法律认定。

## 如何限制幻觉

- Mock/模型输出受结构化 Schema 约束，未知值为 `null`。
- 提取值保留证据 ID、定位、置信度和确认状态。
- 关键事实须人工确认；模型不能直接生成最终事实或法律结论。
- 原始材料中的提示性文字作为不可信数据处理，不能改变系统指令。
- 用户陈述与证据支持事实分开存储与展示。

## 角色权限

普通用户只能访问自己的案件；复核员只能访问分配案件且不能改原始文件；管理员负责测试案例、复核分配和脱敏审计。所有关键 Route Handler 都在服务端验证角色、所有权或分配关系，页面隐藏不是授权边界。

## 真实迭代问题与修复

| 发现 | 修复与学习 |
| --- | --- |
| 有演示账号但没有完整演示资料 | 增加 8 份可重复生成的虚构资产和幂等演示模板。 |
| 复核员缺少退出入口并被带到错误页面 | 统一角色导航、默认落点、退出 Session 与页面级路由保护。 |
| 手动填写字段仍显示待确认 | 将字段确认状态和证据支持状态拆分，兼容历史三态。 |
| 演示案件初始化异常 | 用模板唯一标识、初始化状态、事务补偿和稳定错误码处理半成品。 |
| Server/Client 传递 SQLite 行时报序列化错误 | 建立 Zod DTO mapper，去除内部存储键、哈希与二进制。 |
| 开发 CSP 阻断调试 eval | 仅开发环境加入 `unsafe-eval`，生产策略保持禁止。 |
| 第 4 步未完成却进入第 5 步死路 | 增加明确前置提示、回退动作与提取汇总。 |
| 八步状态机不一致 | 以服务端统一派生工作流替代页面各自推测。 |

## 结果与验收

最终以 8 份虚构证据、18 项提取结果跑通普通用户完整流程；管理员正常分配复核员，复核员仅查看已分配案件并提交说明。自动化覆盖单元、集成、端到端、权限、删除和导出；最后完成完整人工测试。

## 已知限制与商业化前提

正式使用前需要企业认证、生产数据库与私有对象存储、真实 OCR/LLM 的数据处理评估、备份恢复、监控、渗透测试、隐私合规、法律专业审查与明确的用户支持流程。当前没有真实用户、营收、准确率或效率数据，因此不对商业价值作量化声明。

## 反思

最重要的变化不是增加更多页面，而是从“功能存在”转向“用户能完成闭环”：统一状态让页面提示一致；可追溯确认让 AI 只承担候选整理；完整角色验收让前端体验与服务端权限同步。下一步若继续，应先验证真实但合规的工作流需求，而不是盲目扩展功能。
