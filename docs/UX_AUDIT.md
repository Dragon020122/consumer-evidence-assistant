# 可测试性、工作流与 UI 审计

审计日期：2026-07-11。范围覆盖普通用户八步流程、三种角色、服务端授权、演示数据、上传/提取/时间线/矩阵/导出、页面状态与现有自动化测试。

## 结论

现有服务端所有权、复核分配、文件签名校验和角色授权边界正确，应完整保留。主要问题集中在演示可重复性、状态语义和流程反馈：已有种子只有案件基础字段，没有可上传的完整证据包；案件字段以 `CONFIRMED/PENDING/UNKNOWN` 同时表达填写与确认，无法表达 AI 来源或证据支持；上传页是单文件表单，缺少材料检查清单、演示载入、处理进度和文件管理；后续页面以局部链接串联，没有统一步骤状态；时间线为空、未确认时的错误提示过于技术化，导出也没有“不完整草稿”路径。

## 发现与优先级

### P0：演示与安全边界

- `.env.example` 尚无 `DEMO_MODE_ENABLED`，服务端没有统一的“非生产且显式开启”守卫。
- 种子案件字段与指定演示事实不一致，且没有配套 PNG/PDF/TXT；现有 E2E 只动态创建三份 TXT。
- 演示创建、载入和重置必须继续经过案件所有权、上传验证、提取校验及导出链路，不能直接写最终表。

### P0：字段状态模型

- 创建表单要求每个字段选择确认状态，手动输入默认仍为待确认。
- `details_json` 缺少独立证据支持状态和保存时间；历史三态数据需要兼容映射。
- AI 提取表使用另一组 `PENDING/CONFIRMED/MODIFIED/UNKNOWN`，中文标签与案件字段没有统一语义。

### P1：工作流与阻断

- 案件状态是后端粗粒度阶段状态，并不能直接表示八步 UI 的完成/缺口/冲突。
- 无证据时无法提取是合理真阻断，但页面只给出空态；未确认任何提取结果时无法生成时间线；未确认时间线时无法生成矩阵和材料。
- 缺少材料本身不应阻止查看提取、缺口或初步整理；完整导出前应明确列出最低建议材料，并允许生成带“不完整”标记的草稿。

### P1：上传体验

- 缺少类别说明、优先顺序、支持格式/大小、单项/全部演示载入、上传进度、预览、改分类、重命名、替换和失败重试。
- 服务端已有 MIME、扩展名、魔数、大小、数量、摘要去重、私有存储和所有权校验，可作为所有演示载入的唯一入口。

### P2：页面与响应式体验

- 案件详情将基础信息和上传并排，长表单在窄屏滚动较长；后续页的步骤数字不一致（9 步与需求 8 步）。
- 全局有 loading/error/not-found，但页面级异步操作缺少一致的成功、失败、保存时间和重试反馈。
- 复核/管理页功能边界已经清晰，本轮以统一状态标签、空态和响应式间距为主，不重做视觉风格。

## 测试缺口

- 已有完整服务层 E2E 覆盖三份 TXT 的主链路和删除，但未验证演示环境守卫、完整八份资料、字段状态迁移、软提醒、不完整草稿、仅当前用户重置和生产隐藏。
- 角色导航/退出已有专项测试；应保持并加入演示功能的跨用户 IDOR 回归。

## 修复策略

1. 建立单一演示环境守卫与可重复生成的八份虚构资料。
2. 兼容迁移字段状态，并把证据支持作为独立维度。
3. 演示案件、演示载入和重置全部走现有服务层安全校验。
4. 以派生式工作流检查清单替代新增复杂状态机；保留数据库案件状态用于后台处理。
5. 只在“没有任何可处理输入”等技术前置条件上硬阻断，其余缺口使用解释充分的软提醒；导出显式标记完整/不完整草稿。
